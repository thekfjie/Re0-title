# 82 个参考样本：证据与假设

来源是用户提供的 ZIP，包含 82 张 3200×1440 手机视频截图，未提供字体文件、矢量源文件或设计稿。全部已查看，编号按文件时间排序。`references/dataset.json` 保存逐样本文字、观察到的断行、脚本计数、形态素和布局类别；`analysis/measurements.json` 保存独立图像测量。原图只用于本地研究，不随公开站点传播。

## 先排除截图污染

左上 bilibili 标记、左下观看人数与中文翻译均不是日文标题。部分中文翻译在上方（#63、#73）、左侧（#17）或图中文字间（#80）；不能把简单全图阈值 bbox 作为标题 bbox。#25、29、31、60、65、69、70、77、82 是白底或浅底变体。#27 雪花、#31 花瓣、#43/53 渐变、#50 倒影、#54 血迹、#62 彩色背景不能参与普通黑底墨迹测量。#69 遮挡字保持未知。

## 重复出现的规律

1. 字形角色发生分化：汉字通常粗、直、密；假名常有明显书写曲线且更小。#2「再会の魔女」、#30「待ちかねた再会」、#48「聖域の…」支持混排假设，但无法仅凭截图确定字体名。
2. 单字是强调单位之一。#30 的「待」蓝、「再」粉，不是把整个「再会」同色处理。#33、35、38 的「の」着色，说明助词并非永远白色或不能强调。
3. 汉字也不等大：#2「魔」比「再会」「女」大；#12「王」大；#14「病」大。仅做“汉字大、假名小”不足以描述层级。
4. 基线、字面高度与字距都变化。假名嵌入大字周围，#8、#17、#48 的字间及行间关系明显不是固定 CSS 行高。
5. 多行保持阅读顺序，并有有限的几何母式。重复词会成为跨行对照锚点，例如 #24 的「騎士」、#60 的「最も…英雄」。
6. 黑底、白字与局部强调色是主要视觉方向。也存在灰字、纯色整块、低对比与白底例外；“关键词必着色”并不成立。
7. 装饰效果是额外层：#50 的倒影、#58/81 的纹理、#75 的发光，不能用字号参数复刻。第一版引擎不把它们当通用模板。

## 从样本归纳的家族

`compact_anchor`：极短标题，大字构成紧凑核心，#6、11、18、31、52、76。

`interwoven`：单行大内容字与较小连接部分交错，#2、5、9、14、30、35、59、74。横向锚点与混合字号在数据中高度重合，合为一个家族。

`wide_block`：连续内容字或纯片假名/拉丁字构成横块，局部层级，#19、22、41、54、57、62、63。

`offset_stack`：二至三行错位，组间有句法关系，#1、3、4、7、20、24、44、60、72、78。层级可发生在各行内部。

`alternating_steps`：窄而高，阅读块左右交替，#48 是最清楚的例证，#80 为复杂变体。仅两个样本支持，不能认定其参数分布已学稳。

这些是人工操作性分组，不是经聚类证实的“真实设计模板”。82 张来自同一系列，独立性与泛化范围有限，不进行小样本神经训练。`family_summary.json` 的类别数量是人工注释数量。

## 测量可靠性

像素层可测 foreground bbox、墨迹覆盖率、墨迹质心及颜色簇；由尺寸与颜色推字体、token 字号或真实轮廓缩放只能作假设。JPEG 抗锯齿、视频帧过渡、白字裁切和装饰会影响阈值。缺乏证据的 token bbox、字号比、字距保留 null，不用虚构数字填满表格。

逐字符精细标注仍是后续研究工作。第一版支持数据修订与参数再拟合，不能宣称已完成字体识别或达到设计师水平。

补充六张的 36 个字符/连续假名单元细标，含原图 bbox、观测 RGB、视觉角色与可审查误差（通常边缘 ±3 px，人工分界最高 ±12 px）。`fine_annotations.json` 严格使用 ink 高度比，font-size 与 font-family 留空。#30「ちかねた」合组，不冒充逐字符无误差轮廓。#48 的标点另计，避免缩小标点夸大正文层级比例。

前 24 张全部可靠黑底，标题框宽度中位占画布 0.855；后续可靠黑底样本为 0.656。墨迹留白中位分别 84.8% / 91.6%。因此候选使用多种尺度，不能把全部样本平均成唯一“字号规则”。

2026-10-11 颜色复查：全部 82 张再检视，逐样本补充 96 个出现位置明确的着色单元，区别词内锚点、连接点、重复对照、灰色与整块效果。见 `analysis/color_reference_review.json` 与 `color_rules_revision.md`。不把像素色簇数等同语义重要度。

# 可操作规则，非字体识别结果

规则先由 82 张截图的视觉证据提出，量化数据用于校验范围。`config/*.yaml` 集中保存可调参数；初始参数是实验起点，不冒充从逐字符标注精确拟合。

字号按 token 重要度与字符脚本共同分配。一个名词中仍允许单个汉字是主锚点。平假名有较小的默认字面，但不能把所有假名都设为低权重：#10「や」、#33「の」、#48「り」「ま」也可着色。混排字体通过 kanji/kana 角色选择，字形本身用实际 ink bbox 定位，不能用 CSS em 方框代替。

阅读顺序保持原始文本。形态素内部默认不拆；连续助词依附前词。标点与附属内容一起断行，禁行首标点、禁行末开括号、禁止标点独占行。输入过长时在安全字符边界拆分超长 token，但记录其惩罚。

断行使用 token 边界束搜索，同时考虑语义切口、行宽不均、模板预期行数。每个家族产生多种字号与偏移组合。阶梯家族按语义块横向交替，并非逐字符竖排；偏移以占用区域归一化。

黑底使用白色主体，白底使用深色主体，配少量强调；默认自动选择无彩色、单色或双色，最多两个颜色角色。灰色属于可见层级。颜色选择可用于重复关系，不能只按 POS 决定。参考白底/纹理/倒影变体不自动推广为黑底生成规则。

间距使用字形 mask 的共同扫描行计算最小轮廓距离，允许 em 方框互相覆盖，但不能发生实际笔画严重碰撞。异字号、异字体配对每次测量，禁止固定全局 letter-spacing。标点缩小并下移，句尾允许小幅悬挂但仍必须在画布安全边界内。

整组先按真实路径界限缩放，再按面积加权墨迹质心居中。目标是保留周围留白，不是填满画布。各家族有不同目标 box fill。质量分数只描述已定义的约束和分布，不能等同于“好看”。

默认不旋转字符。参考 #81 的旋转与残缺纹理是特殊效果，不在本版常规母式中。模拟退火可改变行偏移、字块上下位置、字号、横向缩放及锚点色；原文、禁则和字体权限是硬约束。

## 本轮规则修正

`template_rules.yaml` v3 增加明确的字符尺寸序列、基线序列、假名尺度变体、强调位置策略和错位行序列。连续汉字不再只有首字大、其余固定小；假名根据自身 ink 高度与角色变化，连接词仍通常较小。颜色可以落在高重要度词首、词末或假名/助词上，不把“词首汉字染色”当唯一规律。

短标题排除不适合的三至五行家族；包含成对「…の…と、…の…」结构时保留四行候选。仍搜索多个断行和多种家族，不将成对结构强制成一种唯一成品。禁则是硬约束，连接用法「と / いう」的断开另行禁止。

退火不再随机修改颜色：现有目标函数没有独立颜色关系评价，随机换色只会破坏已经确定的强调关系。颜色变化由可复现的 style variant 控制；退火优化位置与字形尺度。

## Seed 与颜色判断修正

Seed 现在先选整体变化参数：留白、锚点/假名比例、基线相位、错位方向和幅度，再产生局部优化。完整变化参数随 JSON 保存。着色增加对比度、强调面积、重要度和参考颜色数量先验；双色不再是默认固定答案。白底使用独立深色配色。细则与实测见 `input_seed_color.md`。

## 颜色 v4

语义 importance 与颜色视觉锚点分开；内容字优先，短 `AのB` 单桥可作为候选，重复「的／の」不自动批量着色。自动强调不随机归零，纯前景色单独选择。色值与出现位置可手动覆盖，并支持透明 PNG/SVG。证据、条件与限制见 `color_rules_revision.md`。

# A：无大模型基线

生产生成路径不调用 LLM、VLM、CLIP、OCR 或视觉 embedding。参考分析只使用人工查看、阈值图像处理及统计。

文本先经 SudachiPy B 模式做形态素分析。POS、汉字占比、长度、重复与句首/尾位置产生 importance。三个可配置启发式为 balanced、kanji_anchor、semantic_nouns，分别注重默认平衡、汉字锚点和名词语义权重。`experiments/ablations.py` 在四条标题上做探索性消融；不是审美排名。

公式的默认形式是 `POS基值 + 汉字占比×bonus + capped长度×bonus + 重复bonus + 边缘bonus`，助词与标点单独使用低基值。它无法充分识别隐喻、上下文与反讽；B 用语义计划替代这部分，后续过程完全共用。

## 搜索

每个合格家族尝试多种行数。token 边界的 beam search 保留 32 条部分路径，总代价含目标行宽差平方和、切口惩罚与超长 token 紧急拆分惩罚。助词/标点不可作为下一行独立开头，闭标点禁行首，开括号禁行末。至少生成多个家族与三种尺度，再从候选池按家族多样性和分数选出 4–8 个答案。

形态素可以包含多个脚本。字体按 kanji/kana 角色分 run，每个 run 由 HarfBuzz shaping；拉丁 ligature 与 kerning 保留 advance/offset。日文字形通过 mask 共同扫描行测安全最小距离，可以让字面方框嵌入但保持笔画间距。FreeType 提供真实 mask，fontTools 提供相同字体实例的 SVG path 与 outline bounds。最终 SVG 包含 path，不引用字体 URL。

布局变量是字形 ink x/y、size、scaleX/scaleY、color 与行 offset。默认 scaleY=1、rotation=0；没有证据支持常规标题普遍旋转。本版退火开放上下偏移、行平移、字号、横向缩放、水平位置，最多 32 步。字体名和文本不可被 mutation 改动。禁则、溢出与显著笔画碰撞是候选淘汰条件。

## Score 定义

| 项 | 计算 | 局限 |
|---|---|---|
| Balance | 实际墨迹中心离目标 (0.5,0.5) 的归一化距离 | 居中校正后区分力有限 |
| SemanticEmphasis | 字符重要度与 ink bbox 面积相关性映射到 0–1 | 字面面积不等于感知显著性 |
| SpacingQuality | 共同扫描行的最小墨迹间距/em 与目标间距的绝对偏差，经指数映射 | 1/4 栅格量化会影响极小字 |
| TemplateConsistency | 行数是否属于所选家族 | 人工家族定义，不是设计真值 |
| WhitespaceQuality | ink 总体 bbox 占画布面积与家族目标的偏差 | 与 ink 覆盖比例分开记录 |
| Rhythm | 字号离散程度，饱和到 1 | 不代表越变化越漂亮 |
| CollisionPenalty | 240px 宽 mask 栅格的重叠比例 | 约束检查为低分辨率，非逐像素无误差保证 |
| OverflowPenalty | 画布外 mask 与字形范围 | 安全边界同时用于 fit |
| KinsokuPenalty | 非法行首/行尾数 | 不涵盖出版级 JLREQ 全部规则 |
| AwkwardBreakPenalty | 束搜索断行代价/行数 | 包含行宽分布和语义代理，不是纯语义分 |

权重全部在 `layout_weights.yaml`。正项加权、罚项减权。合格候选允许极少量栅格重叠误差（0.3% 上限），Benchmark 记录实测最大值。分数用来比较实现中的候选，不能与人类审美评分互换。

## 参考统计与泛化

占用面积参数用可靠黑底样本拟合，排除 Benchmark 的参考 ID，见 `fitted_layout_statistics.json`。样本不足四个的 wide_block、稀少的 alternating_steps 保留可审查假设。其他层级/字距参数是初始实验参数，没有伪装成逐字拟合结果。

seed、字体 SHA256、token 角色、布局家族、完整配置 hash、候选池数量、score 各项与所有字形位置均记录。随机源固定到每候选，重跑同一 Python 环境得到同一 SVG；跨渲染库版本或 Python/浏览器端不保证 bitwise 一致。

探索性消融共 20 次（四文本×五设置）：没有一种 importance 启发式在全部标题上占优，固定间距也在两条标题上获得更高内部 score。因而保留可配置启发式与光学字距，不把内部打分当审美结论。

颜色质量现在加入 Score：对比度通过率、着色区域的重要度、强调面积克制程度、参考颜色数量先验。单色/双色/统一前景色为显式选择时不使用自动数量先验。小字低于 4.5:1、大字低于 3:1 的配色在输出前改为主体前景色。该工程可读性门槛不是风格相似度或审美证明。

# B：语义规划与共用布局

`llm/planner.py` 使用 OpenAI Responses 的严格 JSON schema。LLM 输入原文、Sudachi 分词与参考家族统计，输出分词修正、semantic_role、importance、visual_role、家族建议与强调关系。没有绝对坐标，没有模型生成 PNG。

LLM 输出的 token 必须逐字符重建输入，role/importance/family 必须在允许范围；新增坐标字段、遗漏标点、改写原文、非法强调子串都拒绝。规划失败明确返回错误，不默默把 A 输出冒充 B。B 与 A 使用同一 `LayoutEngine`、`Renderer`、`FontProvider`、字体字节与约束。家族建议改变搜索优先顺序，并不免除硬约束。短语强调关系转换为短语内部的首个内容字符锚点。

## 已执行与未执行

20 条标题的冻结语义 JSON 是本次会话助手产生的模型辅助研究产物，保存为 `session_plans.json`。它们在对照前冻结，记录 provenance，所有计划经原文重建校验。B 使用这些计划生成了完整候选，与 A 具有相同字体、seed 和配置。

当前环境没有 `OPENAI_API_KEY`，因此没有执行在线 Responses 调用。不能把冻结计划的读取时间计为 LLM 延迟，也不能计算未知调用成本。`--live-llm` 可以在配置 Key 后用完全相同 Benchmark 重跑，记录实际模型、response ID、usage 与 API latency。默认模型名是可改的实验配置，不是“最新”或“最佳”结论。

## Vision Critic

`llm/critic.py` 是可选实验适配器，接受 1–4 张参考图与 4–50 张有效候选，返回严格候选 ID 排名和理由。ID 不得遗漏、重复，Critic 只能排名，不能绕过共用约束。默认关闭，未在线运行，未纳入“B 更好”的结论。无证据时不加入 CLIP/DINO 依赖，也不训练神经网络。

## 部署与秘密

Key 只放服务端环境变量，不进入 JavaScript、仓库、模型输入日志或可下载参数。模型仅收到文本/参考统计；规划器不上传字体本体。Vision Critic 若显式启用会发送渲染图与选择的参考图，应在私有研究范围使用。

在线浏览器版可以演示 20 条固定文本的冻结 B 计划；任意新文本的在线 B 需要 Python 后端实际配置 API Key。两者在 UI 中分别标明，不能作为生产实时推理的等价证据。

官方技术来源：OpenAI Structured Outputs / Responses 文档、HarfBuzz shaping 文档。接口结构经文档检索后实现；当前无在线调用凭据，仍需真实 provider 集成验证。

## 兼容服务与在线网关

按用户选择增加 OpenAI 兼容服务。`LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY`、`LLM_API_STYLE=chat_completions|responses` 由服务器管理员配置；`LLM_JSON_MODE=json_schema|json_object` 适配提供商能力。返回仍必须通过同样的严格计划验证。JSON-object 模式也不允许多字段、丢字或坐标。

Sites Worker 的 `/api/plan` 只返回验证后的语义计划及模型/usage/延迟，浏览器随后将计划交给同一个 HarfBuzz 排版 Worker。模型看不到用户字体文件。`/api/status` 只暴露是否配置密钥，不返回密钥或上游地址。Python 服务同样支持兼容路径。

已有接口协议测试使用 stub，证明请求封装与边界验证，不代表真实服务可用或模型质量已测。没有配置时保持明确的固定计划实验，不把它标成 live B。

实际兼容服务报告 `gpt-6.1-sol`，Chat Completions + strict JSON schema 已验证。使用低 reasoning effort 与 max_completion_tokens；完整 20 条真实输出已保存。页面内复用语义计划不代表再次调用上游；重规划按钮会发起新请求。

# A / B 实时对照

20 条标题（13 条参考文本、7 条新增输入），每方案 6 张，合计 240 张。相同 Noto Sans JP Black、Shippori Mincho SemiBold 字节、dataset、seed=42、配置、Renderer 和硬约束。B 的 20 条语义计划均来自实际兼容服务调用，服务报告模型 `gpt-6.1-sol`。

默认 47/81 条的强调位置与参考没有交集。它们通常已有颜色，只是落在不同字符上；这与“没有强调色”是不同问题。现有词性、汉字比例与词首优先规则过于粗糙。

逐图观察的具体差异：

下一轮应把颜色角色拆为主锚点、关系锚点、构图桥接、弱化、整词和局部单字；语义重要度与视觉作用分别计算，再与布局一起选择。颜色数量、位置、灰度和色相分别评价，不把一个 Jaccard 分数当作好看。

## 比较依据与边界

- 断行：直接比较人工转写的每行字符串；行数一致另外记录。
- 色位：以 Unicode 字符出现位置建立集合，Jaccard = 交集 / 并集，重复字符不合并；两边都没有强调时为 1。参考包含灰色层级和近似颜色标注，生成以不同于前景色的 glyph 为强调。没有比较精确 RGB，也不能把高重合度当作色彩协调度。
- 几何：参考和生成均相对于整张标题画布测量。比较 ink bbox 宽高比、区域覆盖、ink 覆盖及像素质心；只对 59 张可靠黑底统计。
- 字面高度：字符 ink 高度 / 各自汉字中位 ink 高度，与 6 张细标比较。假名组的整体 bbox 不冒充逐字高度。
- 文字完整：核对行拼接及可见 glyph 转写；未知被遮挡文字不参与匹配结论。
- 发光、倒影、碎裂、纹理、渐隐等尚无对应 Renderer 处理。特殊样本保留展示，不能宣称复刻。
- Python 使用 Sudachi，在线浏览器使用 Kuromoji。冻结对照图由 Python 生成；在线选同一标题会重新生成，不承诺跨端逐像素相同。

本次范围是全部参考与 A 的比较；既有 20 条 A/B × 6 候选和实时语义计划保留，见 `comparison.md` 与 `/benchmark/`。没有补造 82 条 B 结果，也没有预设语义模型能解决共同的几何和排名问题。

## 参考实际支持什么

单个词内部着色很常见：#5「約束」的「束」、#9「意味」的「意」、#49「咆哮」的「哮」。因此词的重要度只能帮助选词，不能要求全词同色。片假名也会只着色一段，例如 #11「ム」、#56/#72「ガー」。

#33「少女の福音」、#35「命の価値」、#38「死の味」、#55「氷炎の結末」用小连接字「の」建立局部视觉对比。#39 还有多色装饰性例外。这五张不支持“助词越重复越重要”：桥接色是视觉功能，助词的语义权重仍低。

#24 的两个「騎」分别灰/紫，#60 用「新」与第二个「英」形成跨行对照；#48 分散到汉字与假名位置。同字的各次出现可以承担不同角色。重复字符串不应该被全局替换成同一种强调色。

灰色层级、整段灰字、纹理整块和局部彩色须区分。#26/#62/#65/#70/#73/#75 没有观察到明确局部色点，其中包含白字、浅灰或发光例外；此前像素统计的“无彩色”还包含不少灰白层级标题。不能把所有无彩色理解成缺字，也不能把灰色视为强语义强调。

没有证据证明某种意义必定对应某种色相。蓝、粉、黄、绿、红等是可选的视觉关系；故事上下文、角色颜色或场景意象可能有影响，本资料不足以验证这种映射。

## 旧规则的问题与修改

旧自动模式随机抽取零色，用户难以判断是否失效；B 的强调子串会命中每个重复位置，错误计划中的「的／の」可能全部染色；同时把 semantic importance 用作颜色的唯一质量代理，使视觉连接点与语义重点混淆。旧代码还把强调词中的每个字符加入全局集合，可能放大其他位置的同字，这一处理已移除。

现在分别保留：字号用语义 importance；颜色用内容角色、词内字面位置、模型锚点、弱概念先验和视觉桥接条件。A/B 共用 `engine/accent.py` / `web/client/accent.js` 的同一决策定义，54 组固定输入通过两端一致性检查。

自动候选优先选择一个内容字；双色模式可选第二个不同内容位置。重复词默认只选一处，重复助词不选。只有较短 `AのB` 结构（最多六字、一个「の」、两个内容块）允许一类候选以「の」作视觉桥接；中文「的」不借用这个日文特例。LLM 提议仍经过相同保护条件。

“自动强调”不再随机抽取零色；“统一前景色”明确保留无局部色的结果。这是产品行为选择，不声称参考没有无彩色标题。仅有功能字/标点、无可读强调色或用户选择统一前景色时仍可能没有自动色点，结果会记录原因。

自动色对比度不足时先从当前配色选择可读强调色，找不到才恢复前景色。手动指定颜色按原值保留，低对比度给提示。前景色可自定义，强调色池支持 1–8 个任意 `#RRGGBB`；自动数量预算仍受单色/双色约束，色池有八种不意味着必须涂八种。

## 局部编辑与透明导出

结果下方逐字符选择；Shift 连选，Ctrl/Command 多选。相同字按 Unicode scalar offset 区分：`{start,end,color}`，区间 `[start,end)` 相对于最终排版文本。选择第一个「の」不会修改第二个。编辑在全部候选间保留，改标题时清除；可单独恢复或恢复全部自动色。

局部编辑直接修改 SVG glyph outline 的 fill，布局与字号不变，不调用模型或重新搜索。PNG 从同一编辑后 SVG 渲染，两个格式和参数 JSON 一致。连字共享一个轮廓时，选择其部分字符会对该轮廓着色；日文基准字体的常见单字没有这个问题。

下载区“透明背景”立即移除全画布 rect，PNG 背景 alpha=0，SVG 保留可独立使用的轮廓。透明预览用与预期画布匹配的棋盘格。颜色可读性按所选黑底/白底检查，放到另一种背景时需重新看效果。

FastAPI `/render` 接受 `custom_colors` 和 `color_overrides`，拒绝无效 HEX、越界区间及超限颜色。上传字体隔离策略不变，SVG 不内嵌字体文件。

# 中文输入、Day/Night、Seed 与颜色审计

以下记录初次 Seed/颜色审计；颜色部分保留为历史结果，当前 rules v4 行为与 82 张复查见 `color_rules_revision.md`。中文转换、明暗与 Seed 说明仍适用。

2026-10-11。结论：旧 Seed 有作用，但影响偏细小；旧颜色规则过于固定，且缺少可读性评价。新版扩大整体变化，收敛默认着色，并保留人工控制。

## 中文输入

三个入口共用排版引擎：

- 自动转为日文汉字：本地词典按最长词组将简体/繁体转换为日本新字体，保留假名、标点、数字、拉丁字母。不会把中文语法翻成日语。
- 中文标题 → 日语：服务端严格 JSON 翻译，再把日语交给 A 或 B。A 的布局仍无模型，选择这项会明确显示“中文翻译 + A”。
- 保留原文：跳过转换，用上传字体覆盖能力决定是否可画。

例：字形模式将“圣域的终结与崩坏的开始”转换为“聖域的終結与崩壊的開始”，保留“的”，不声称这是自然日语。真实服务翻译实测为“聖域の終焉と崩壊の始まり”。两者目的不同。

原输入不被覆盖。排版文本可编辑、重新转换。模型翻译允许意译与信息偏差，必须查看译文；一条实测不能证明任意中文的翻译质量。字体缺字会明确报错，不偷偷删字。简繁一对多通过词组减少歧义，不能保证人名、专有词和所有异体的唯一正确转换。

词典固定 OpenCC commit `8cf737a4e193db27d675b2ce9867d84aace33745`，保留 Apache-2.0 许可、源文本和 SHA256。实现是 Compatibility → ST 最长词组/字符 → 日本新字体逆映射的衍生转换器，不冒充完整 OpenCC runtime。源数据与生成过程见 `assets/conversion` 和 `scripts/build-kanji-dictionary.py`。

## 明暗

右上 Day/Night 只改变界面，并将偏好保存在本机。生成器、对照页、研究页共用偏好。

“画布与复现”的 Night/Day 改变导出背景与对应字体颜色。白底单独使用深蓝/深粉等配色，不直接沿用夜间浅粉。透明导出不包含背景；颜色按选中的预期画布检查，换背景展示时仍需重新评估。双色表示最多两个不同强调色，短标题、单锚点计划或灰白调色板可能只出现一个；不为凑数把无关字染色。

## Seed 是否有用

旧路径只改变小幅 scaleX、baseline 抖动与退火随机数；断行/家族/三个尺度都被穷举，优化会让不同 Seed 回到相近结果。用户观察成立。

新版 Seed 先决定字号关系、假名比例、基线相位、错位方向和幅度、留白、强调方案，再进行局部优化。“换一组”产生新 Seed；数值收进复现设置。它不控制翻译、分词、模型采样，不保证每个数字都获得另一种完全不同的布局家族，也不保证换一组更好。

四条标题 × Seed 42/43/77 × 六候选，用相同字体比较同家族、同断行的匹配候选：

| 指标 | 旧版 | 新版 |
|---|---:|---:|
| 可匹配候选对 | 46 | 47 |
| 位置变化 RMS 中位（画布归一化） | 0.0170 | 0.0293 |
| ink 覆盖比例相对变化中位 | 3.1% | 13.7% |
| 着色模式改变的候选对 | 11 | 42 |

该比较排除断行变化，匹配数量不完全相同；衡量的是可见变化而非审美提升。输入文本、同一模型 plan、字体字节、配置、软件版本和 Seed 一起固定才可复现。导出 JSON 保存完整 plan、变化参数和色彩决策。

## 字体颜色判断是否合理

旧版先按 token importance 排序，选词首/词末/连接字，再依次涂两个强调色。LLM 指定锚点时覆盖规则，但颜色没有评分项。它能表达层级，却不能说明某个词天然应该是蓝或粉，也没有依据让每个标题都用双色。

59 个主黑底样本的近似色簇数：19 个无彩色、37 个一种彩色、2 个两种、1 个四种。JPEG 阈值与着色区域会影响计数；这是数量倾向，不是精确设计用色真值。新配置自动数量概率约 32% / 63% / 5%，不是词义到色相的模型。最终候选还经过评分与家族/断行多样性选择，实际比例不会完全等于抽样概率。

新版保持两种职责：importance/明确语义锚点决定着色位置；palette、参考数量先验、Seed 和候选策略决定色相与数量。参考中的助词强调保留为一种候选，不伪称助词的语义重要度高。LLM 锚点按完整子串覆盖，重复项使用相同色彩角色。

新增颜色质量由对比度通过率、着色部分 importance、着色面积克制程度、颜色数量先验组成。面积使用 glyph bbox，非精确彩色 ink；它是可解释代理分，不是人类审美。显式“单色/双色/统一前景色”覆盖数量先验。

可读性门槛：主体字 3:1，小于 24px 的字 4.5:1；不足则恢复前景色并记录原因。是工程阈值，不宣称自动满足全部无障碍或参考风格。“着色依据”逐项显示文字、原因、重要度、色值和对比度。

本轮四文本 × 三 Seed × 六候选的实际彩色数分布：0 色 25 张，1 色 40 张，2 色 7 张。夜/昼 × 四配色 × 四候选共 32 次检查通过最低对比度、禁则、边界与现有碰撞阈值。详细逐字理由在 `analysis/seed_color_audit.json`。

## 验证与限制

浏览器实测：无模型汉字转换、真实翻译、可改译文、B 接收日语、界面与画布独立、透明 PNG、移动端、主题保存，以及换字体/画布/Seed 不重复调用模型。测试见 `experiments/chinese_theme_seed_color_qa.mjs`。

A/B 复用同一 20 条真实 plan 重渲染 240 张，原文/禁则/边界均通过。新增颜色评分使内部 Score 尺度改变，不能直接和上一版均值比较。尚无独立审美评审；改进了行为和可解释性，不代表已证明最接近参考或 B 普遍更好。

# 字体与任务生命周期

没有商业字体。按用户对尚未开放的研究版的追加授权，`assets/open-fonts` 显式收录 8 组 SIL OFL 1.1 字体及完整许可证、来源与 SHA256；它们可进入 Git、Docker 和浏览器资产。此例外仅适用于该开放字体清单。商业字体、上传字体和管理员私有字体仍不入库、不进入静态产物。

`FontProvider` 是可替换协议，当前有 `BundledFontProvider`、`UploadFontProvider`、`PrivateFontProvider` 和浏览器 `BrowserFontProvider`。服务端：24 MiB 单文件、8 文件/64 MiB 单会话、扩展名/MIME/sfnt 文件头/必要表检查。大请求含 chunked body 在 multipart 解析前限制。文件名不作为路径；随机 ID + 扩展名存储，目录按会话秘密的 SHA256 隔离，权限 0700/0600。

上传的 fontTools 检查运行在内存与时间受限子进程。渲染运行在独立子进程，每任务独立目录，CPU/内存/文件大小限制和 50 秒父进程超时。任务只复制指定会话的字体，完成或失败都删除字体副本与任务输入。原上传文件有一小时 TTL；清理线程每 60 秒运行，重启时也清理。任务输出同一 TTL、同一会话验证。只允许下载 `candidate-[1-8].png/svg`，没有字体下载路由。

cookie 是随机 256 bit bearer session，HttpOnly、SameSite Strict。生产 HTTPS 时设 `SECURE_COOKIES=1`。没有跨源上传/写入许可。`DELETE /fonts` 清理该会话字体与结果。任务结果不可跨会话读取，已通过两个 TestClient 验证。

管理员字体只有 `PRIVATE_MODE=1` 且设置 `ADMIN_TOKEN` 才通过 Bearer 授权可用。`PRIVATE_FONT_DIR` 只读挂载，管理员字体不会被 Web 返回本体。普通模式不能列出或使用它们。

浏览器版的用户上传字体只放 Web Worker 内存；不调用上传 API、不写 localStorage/IndexedDB、没有上传字体 URL。预置 OFL 字体有独立资产 URL，以加载字形，并随附许可证；这不会开放任何上传/私有字体。清理按钮释放 HarfBuzz 对象，关闭页面终止 Worker。静态资产只含清单中的 OFL ttf；构建不会扫描系统目录或 PRIVATE_FONT_DIR。字体缺字会报具体字符，不默默用系统字体替补。

本地内存 rate limit 与两并发槽属于单进程保护；生产保持一个 uvicorn worker。扩展到多实例应使用共享队列/限流/会话存储，不能把当前本地目录当跨节点存储。解析器隔离不是完整 OS 沙箱；高流量公网部署还应使用容器资源和反向代理限制。

# 在线部署

提供两个互相独立的部署入口，A/B 在各入口内共用同一渲染系统。

Sites 上部署浏览器渲染版与服务端语义 Worker：HarfBuzz WASM + Kuromoji/IPADIC + OffscreenCanvas mask + SVG path。用户上传字体留在本机 Worker 内存；7 组允许再分发的 OFL 字体可直接选用。任意日文可以走 A；20 条固定测试文本可以查看冻结 B 语义计划。服务端 `/api/plan` 支持配置兼容模型；已接入用户指定的兼容服务并完成 20 条真实调用。Sites 不是 Python 服务。

完整 Python 在线服务通过 Docker Compose 或 uvicorn 启动，提供服务端 font_id、Sudachi、FreeType mask、任务隔离、API B 和 PNG/SVG 导出。生产反向代理启用 HTTPS，设置 `SECURE_COOKIES=1`。当前容器仅打包明确清单中的 OFL 字体，管理员商业字体须另行只读挂载。

静态版与 Python 版的分词器、随机源、mask 栅格和像素 PNG 实现不同。它们复用同一配置、角色和母式定义，但不能把跨端差异算作 A/B 的差异。正式 A/B Benchmark 全部由 Python 的共用引擎生成。浏览器页中的实时 A/B 使用浏览器共用引擎。

## 字体/API

`POST /fonts` 接收 multipart `file`，返回 font_id、family、subfamily、weight、axes、glyph_count、Japanese coverage、SHA256 与 TTL。文件头与大小在隔离进程校验。字体没有可下载 URL。

`POST /render` 示例：

```json
{"text":"聖域の終わりと、崩壊の始まり","fonts":{"kanji":"YOUR_FONT_ID","kana":"YOUR_KANA_FONT_ID"},"mode":"classic","seed":42,"count":6,"palette":"night","width":1200,"height":675}
```

`mode:"llm"` 需要配置服务端 Key；不能静默降级。字体 cookie 随同源请求自动带上，curl 使用 `-c cookies.txt` / `-b cookies.txt`。返回候选配置与 `/results/<job_id>/candidate-N.png/svg`，必须持相同会话才能读取。

`DELETE /fonts` 删除当前会话字体和结果。`GET /fonts/private` 要求管理员 Bearer Token，普通会话不能访问。

Docker 环境 `/runtime` 用 tmpfs，容器停止后消失。单进程有两个渲染槽；长期高并发扩容需要外部任务队列与共享存储，此初版未实现。Docker 镜像已实际构建，并在非 root、只读根目录、tmpfs 的容器中验证 OTF 上传、四候选渲染和 PNG 下载。字体文件下载路由不存在，镜像内仅保留清单中的开放字体，上传字体下载路由仍不存在。

## Sites 语义服务配置

在 Sites 的服务端环境变量中设置 `LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_STYLE`、`LLM_JSON_MODE`，并以 secret 设置 `LLM_API_KEY`。不要写入 hosting.json、Git 或网页。环境变化需部署后才应用。Worker 保持现有私有访问范围。

构建：根目录 `npm ci`，`cd hosting && npm ci`，回根目录 `npm run build`。`npm run build:browser` 产生单独静态版供 Python / Docker 使用；前者产生 Sites 的 client/server 产物。
